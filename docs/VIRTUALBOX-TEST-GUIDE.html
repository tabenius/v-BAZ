v-BAZ · Portable USB · Phase 2

Testing the portable image in VirtualBox

A safe, reproducible route from source checkout to OVMF boot and the two-host-reboot Kali persistence proof—without writing to a physical USB stick.

Recommended environment: Oracle VirtualBox 7 running an x86-64 Ubuntu 24.04 guest. “Openbox” is a window manager, not a virtual-machine platform. Oracle Cloud can run portions of the test, but local VirtualBox gives easier disk access, nested virtualization and controlled reboot testing.

1. Create the test VM

CPU and memory

4 virtual CPUs and 12–16 GiB RAM. Enable Nested VT-x/AMD-V when the host exposes it.

Storage

Use a dynamically allocated disk of at least 120 GiB. The portable raw image is logically 64 GiB and needs working space.

Firmware

The Ubuntu build VM itself does not require EFI. Enable EFI when directly booting the generated v-BAZ disk in a separate VM.

2. Install the build dependencies

sudo apt update
sudo apt install -y \
  git jq gdisk dosfstools e2fsprogs util-linux \
  qemu-utils qemu-system-x86 ovmf systemd-boot-efi \
  curl zstd

3. Check out the Phase 2 branch

git clone https://github.com/tabenius/v-BAZ.git
cd v-BAZ
git switch codex/portable-usb-phase-2

4. Run the fast checks

sh test/test-kali-persistence.sh
sh test/test-usb-layout.sh
sh test/check-wiring.sh

These validate the persistence filesystem, checksum-pinned media staging, partition plan, shell portability and Windows/Alpine configuration contract.

5. Build and OVMF-test the image

sudo sh tools/usb/build-image.sh \
  --populate-host \
  --output "$PWD/vbaz-usb-amd64.raw"

sudo sh tools/usb/verify-ovmf.sh \
  "$PWD/vbaz-usb-amd64.raw" 240

The OVMF script uses QEMU TCG software emulation, so it works without nested virtualization, although hardware acceleration is faster for later nested-guest tests.

6. Add verified Kali media and persistence

Download the desired Kali Live ISO from the official Kali site and compare its SHA-256 value with the official checksum before using it.

sha256sum kali-linux.iso

sudo sh tools/usb/build-image.sh \
  --populate-host \
  --prepare-kali \
  --kali-iso "$PWD/kali-linux.iso" \
  --kali-iso-sha256 '<officially-verified-sha256>' \
  --output "$PWD/vbaz-usb-amd64.raw"
Non-overwrite rule: the builder refuses an existing output image, persistence image or staged Kali ISO. Do not weaken these checks to make a retry convenient; choose a fresh output path.

7. Directly boot the generated image

  1. Create a second VirtualBox VM for the generated v-BAZ host.
  2. Use Linux, 64-bit; enable EFI; allocate at least 8 GiB RAM and 4 CPUs.
  3. Convert the raw image if VirtualBox will not attach it directly: 
    qemu-img convert -f raw -O vdi \
  vbaz-usb-amd64.raw vbaz-usb-amd64.vdi
  4. Attach the VDI as the first disk and boot it.
  5. For Kali-inside-v-BAZ testing, enable nested VT-x/AMD-V for this VM. Without it, use software emulation and expect a substantial slowdown.

8. Two-host-reboot persistence proof

StepExpected evidence
Boot v-BAZ, then boot Kali with persistence enabled.Kali sees the ext4 volume labelled persistence and its / union rule.
Create a uniquely named marker in Kali.Record its content and checksum.
Shut down Kali and reboot the complete v-BAZ host.The marker survives and its checksum matches.
Repeat the complete host reboot once more.The same marker survives unchanged after the second reboot.
Capture logs and exact image/commit identifiers.The proof is reproducible and attributable to the tested build.

This gate cannot be replaced by merely restarting the Kali process: the entire outer v-BAZ host must complete two shutdown-and-boot cycles.

What each environment can prove

EnvironmentGood forLimitation
GitHub ActionsReproducible build, filesystem checks and OVMF boot.Not a durable interactive two-reboot guest proof.
Local VirtualBoxComplete controlled workflow, nested guest, repeated host reboots.Needs ample disk space and preferably nested virtualization.
Oracle Cloud VMFast checks and software-emulated OVMF runs.Nested virtualization is shape-dependent; ARM shapes are unsuitable for efficient x86-64 testing.
